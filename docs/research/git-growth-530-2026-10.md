# Git history growth of the fact base, October 2026

Status: **research for [#530](https://github.com/juev/memcue/issues/530), measured 2026-10-27; product code unchanged.**
The issue stays open: the choice between the variants is the owner's decision; below are a recommendation and the
figures it rests on.

In short:

- In the source clone 122 distinct versions of `facts.db` take 605.5 MiB on disk: all of them are loose objects, none
  is packed. For the measurements these blobs were put into a **new linear repository** (the replica from here on):
  one commit per distinct blob, in order of first appearance. This is not the source commit graph (that one has 1 095
  commits, merges and other files) and not a replay of past traffic. `git gc` on the replica shrinks it to 63.7 MiB
  (29.5 s, peak 2.2 GiB), `git gc --aggressive` to 25.1 MiB (77 s, peak 4.1 GiB). 63.7 MiB is the size of a replica
  that holds only the base's blobs, not of the whole source repository after gc.
- By the model, the transfer is small. Pushing the replica commit by commit, `pack-objects` builds thin packs of
  23.4 MiB in total, median 9.5 KiB: in the median, neighbouring versions differ in 1.4 % of pages, and a delta covers
  them. This is the payload size, not a network measurement. A local fetch over `file://` on the same replica was
  measured separately: it received the same 23.4 MiB. Yet the remote and the second clone store all 605.5 MiB loose:
  a small pack is unpacked into loose objects on receipt (`transfer.unpackLimit` = 100).
- Batching commits (modelled on the replica: the last version of each UTC day instead of every one) cuts loose growth
  15 times, the packed history only 3.3 times, the model transfer by 14 %.
- A text representation of the same data: one JSONL file takes 6.8 MiB after `gc` (9.4 times less than SQLite),
  1.8 MiB after `gc --aggressive`, model transfer 1.7 MiB (14 times less). A file per fact: 5.2 MiB after `gc`,
  transfer 6.8 MiB.
- Three things unrelated to size turned up on the way. A raw copy of the file taken during a write can be corrupt (46
  of 128 copies under continuous writing, synthetic). `memcue dump` loses evidence, author and fractions of a second.
  `Merge` duplicates a version when an already merged state is merged with an old one (reproduced on synthetic data
  through a real `git merge`).

Recommendation: packing the storage (`git gc`) needs no product change, but it was **not checked** on the live
repository, only on the replica. It should be run by agreement, with a backup and without `--prune=now` (section
"Recommendations"). After that, move the source of truth to text (a file per fact or an event log) with SQLite as a
locally derived base. Before that, decide how `Merge` treats a version present in the tails of both sides, and put a
version barrier on the transition. Details, and what was not measured, are below.

## Question

The issue asks to:

1. reproduce the growth on an isolated copy and tell apart the logical size of the blobs, the actual storage (loose
   and pack) and the network transfer;
2. measure a copy before and after a repack: storage size, time, peak memory;
3. compare on one workload the current method, commit batching and at least one change-oriented representation;
4. check a lossless round-trip, diverging histories, an interrupted migration, concurrent writers and rollback.

Scope of this work: research and documentation only. The live repository and the live base were not changed. Nothing
went to the network: all pushes and fetches went over `file://` inside a scratch directory. The report and the JSON
results contain no fact text, ids, object hashes, machine names or private paths; real data appears only as
aggregates.

## How the base is stored now

Everything below was read in the code of this tree (`05cf464`, memcue 0.21.1, schema 6):

- One SQLite base (`internal/store/store.go`). A fact is a chain of versions under one ULID in the `facts` table
  (`WITHOUT ROWID`, primary key `(id, version)`, 16 columns). Local writes neither delete nor rewrite rows: a
  correction, retire, restore, new queries and labels add a version. The exception is `Merge`: it deletes the rows of
  a fact's diverging tail (`DELETE ... WHERE id = ? AND version > ?`) and inserts them again with new numbers.
- The same file holds derived structures: `fact_index` and the FTS5 table `fact_fts` (an index over the last active
  version), the indexes `facts_created` and `fact_index_numbers`, the `stamps` table. The `fact_vectors` table is
  empty: `Open` deletes the vectors of old versions and runs `VACUUM` once (#260).
- `journal_mode=DELETE`: the rollback journal exists only during a transaction; between writes the file is whole.
- Sync is git. `memcue install` sets `memory/facts.db merge=memcue diff=memcue`. The merge driver
  (`memcue merge %O %A %B`) opens `%A` and merges `%B` into it. It does not read the base `%O`.
- `Store.Merge` (`internal/store/merge.go`) finds the common prefix of versions for each fact: it walks the positions
  and compares versions by content (`same`: all fields except the version number). The prefix ends at the first
  position where the versions differ. The tails of both sides are joined, sorted by `(created, author, content)` and
  renumbered (the old tail rows are deleted, the joined tail is inserted); the last version counts as current.
  Versions present in both tails are not collapsed in the join. The version number is therefore not stable across
  machines.
- `memcue dump` is the textconv for `git diff`, one line per version. It does not print `evidence` and `author`, and
  it truncates `created` to seconds. It was not designed as a recovery format, and the measurement below confirms
  that.

## Method

### Real history: the replica

The real-history figures come from a one-off script on one machine. **The script was removed from the publication.**
An independent review found two problems in it. It did not clear `GIT_*` from the git environment for each
subprocess. It deleted directories recursively (`shutil.rmtree`), and the shared measurement module at that time still
replaced an existing path instead of refusing. It was not safe to reuse on someone else's repository. So the real part
cannot be repeated from this tree: all that remains of it are the aggregates in
[`results/real.json`](scripts/gitgrowth/results/real.json).
What the script did:

1. Read the source repository with `rev-list`, `log`, `rev-parse`, `cat-file`, `count-objects` under
   `GIT_OPTIONAL_LOCKS=0`; it rejected any other subcommand on the source repository.
2. Found the distinct blobs of `memory/facts.db` reachable from all refs (`git log --all --reverse --topo-order -m
   --raw`), in order of first appearance. A blob the history returned to later was counted once. Blobs reachable only
   from the reflog, or unreachable, were not sampled.
3. Wrote each blob into a new repository (`hash-object -w`) and made one commit per blob, linearly, with the date of
   the commit where the blob first appeared. The id of each blob in the replica was checked against the source, so
   the replica stores the same bytes. The results have 122 replica commits for 122 distinct blobs.
4. Built five more repositories from the same blobs: the last version of every 5 (`sqlite-batch5`), the last version
   of each UTC day (`sqlite-daily`), every version after `VACUUM INTO` (`sqlite-vacuum`), one JSONL file
   (`text-single`) and a file per fact (`text-perfact`).
5. Measured each repository (see "What was measured") and deleted the scratch with the copy of the facts.

How the replica differs from the real history:

- **Graph.** 123 commits that changed the base (one of them a merge) are reduced to 122 linear commits. Parallel
  branches are lined up by `--topo-order`, an order no machine ever saw. The delta between neighbouring replica commits
  is the delta between neighbours in this order.
- **Transfer.** The thin pack "commit against the previous one" in the replica models a push after every version. What
  past pushes actually sent depended on the state of each machine and cannot be seen from here.
- **Batching.** `sqlite-batch5` and `sqlite-daily` drop the intermediate versions of the replica. A real batching
  scheme would produce other blobs: edits from two machines would pile up between commits.
- **Day boundaries.** `sqlite-daily` groups by commit date in UTC. The owner's local midnight is offset from UTC, and
  the commit time is not the time of the write to the base, so grouping by local days would give other batches.
- **Run environment.** That run did not clear `GIT_*` from the environment. There are no signs of an effect: the
  replica's blob ids matched the source. But that does not prove no command read a foreign config.

### Synthetic workload

`synth workload` ([`synth/workload.go`](scripts/gitgrowth/synth/workload.go)) writes the base through `internal/store`,
that is, with the same code as `memcue add`, `correct`, `retire`, `restore` and dream. The workload is calibrated on
aggregates of the real base:

- 2 400 facts in the first commit, then 122 commits of 136 writes;
- write mix: 14 % add, 45 % queries, 20 % relabel, 13 % correct, 7 % retire, 1 % restore;
- average field lengths as in the real base: content 234, queries 128, keywords 57 characters;
- text is words from an artificial dictionary (Latin and Cyrillic) with a Zipf distribution, seed 530.

Result: 18 992 rows and 4 731 facts against 18 996 and 4 696 in the real base. After each commit the base goes into
seven repositories: `sqlite-every`, `sqlite-batch5`, `sqlite-batch20`, `sqlite-vacuum`, `text-single`, `text-perfact`
and `text-events` (an event log, see below).

The synthetic SQLite file is half the size of the real one (17.0 against 35.1 MiB), and its `facts` pages are 21 %
empty against 53 %. The absolute sizes of the SQLite variants are therefore smaller on synthetic data. It does not
follow that the synthetic data necessarily understates the gain of text: delta and compression depend on the page
layout and the order of changes, and the synthetic data reproduces those only roughly. This pair of runs has
differences in both directions. The ratio of SQLite to `text-single` after gc is smaller on synthetic data (6.0
against 9.4). But `text-perfact` is larger on synthetic data than on the replica (5.41 against 5.18 MiB), and
`sqlite-vacuum` on synthetic data is worse than `sqlite-every` (32.0 against 29.0 MiB), while on the replica it is
better (47.2 against 63.7).

### What was measured

[`gitmeasure.py`](scripts/gitgrowth/gitmeasure.py):

- **logical size**: the sum of `%(objectsize)` of the blobs (`cat-file --batch-all-objects`);
- **storage**: the sum of file sizes in `objects/`: loose and pack (with `.idx` and `.rev`);
- **thin pack of one commit (model)**: the size of the output of `git pack-objects --revs --thin --stdout` for
  `C ^C~1`. This is the program that assembles what a push sends to a remote that already has the previous commit. It
  does not touch the network; this is the payload size without protocol overhead;
- **clone (model)**: `pack-objects --all --stdout` after `gc`;
- **sync (measured, local)**: real `git push` and `git fetch` over `file://` after each commit into a bare remote and
  a bare peer with git defaults. The stream a fetch receives is recorded through `GIT_TRACE_PACKFILE`; for push this
  tracing does not work, and its volume is the thin pack from the previous item. SSH and HTTP were not measured;
- **time and peak memory**: the wrapper [`peakrss`](scripts/gitgrowth/peakrss/main.go): `ru_maxrss` from `wait4`,
  including the child processes git waited for (pack-objects under gc). A process spawned from Python starts with
  Python's own RSS (~58 MiB) and keeps that value after exec, so measuring directly from Python does not work; the
  wrapper's floor is 3.6 MiB;
- **gc**: `git gc -q --prune=now` and `git gc -q --aggressive --prune=now` on a throwaway copy of the repository,
  under `prlimit --as=24GiB` in case memory runs out. `--prune=now` is here only so that no unreachable objects stay
  on the copy; there is no need to use it on the live repository (see "Recommendations").

Environment of the report run: one x86_64 machine, 8 cores, 31 GiB RAM, git 2.47.3, go 1.27.0, SQLite 3.53.1 (Python)
and modernc.org/sqlite (memcue). The memcue binary was built from this tree and called itself `0.21.1+dirty`: the
product code is the same, "dirty" comes from the untracked research files. Each variant was run once: times are
relative, the spread between runs was not measured.

## Results: real history (replica)

Source repository (aggregates only):

- 1 095 commits across all refs, 123 of them change the base (1 merge), 122 distinct blobs. The commits with the base
  fell on 8 calendar days, at most 20 a day. Days here were counted by the commit date in its own time zone, while
  `sqlite-daily` groups by UTC (it also has 8 batches);
- the base's blobs: 2 157.6 MiB logically, 605.5 MiB on disk, none is stored as a delta object; a single one ranges
  from 3.24 to 35.11 MiB;
- `git count-objects -v`: 852 loose objects taking 612.7 MiB; one pack with 7 016 objects taking 4.4 MiB. Everything
  except the base's blobs was left out of the replica.

Why the blobs are not packed: `git gc --auto` packs loose objects when there are "approximately more" of them than
`gc.auto`, which defaults to 6 700 ([git-gc](https://git-scm.com/docs/git-gc)). 852 objects are far from the
threshold. A rough estimate, not a measurement: about 5 800 more loose objects remain to the threshold, and if the
share of the base's blobs among them stays the same, that is several gigabytes.

  measurement, not an experiment with another schema: I did not try a rowid table. `VACUUM INTO` shrinks the file by
  only 14 % (35.1 → 30.1 MiB).

The local fetch received exactly as much as the model thin pack: 23.4 MiB with deltas. Yet the storage of both sides
grew by the full 605.5 MiB. The cause is `transfer.unpackLimit`: if a received pack has fewer objects than this limit
(100 by default, [git-config](https://git-scm.com/docs/git-config)), git unpacks it into loose objects, and the deltas
are lost. A commit with one base is four objects (the commit, two trees, the blob). In `text-perfact` some pushes carry
more than 100 objects (shard trees and fact files), and such packs are kept as they are.

source clone. A replica of the same blobs takes 63.7 MiB after `gc` and 25.1 MiB after `gc --aggressive`. This is an
estimate of what the base's blobs pack into in the replica's linear order. How much the source repository will take
after gc does not follow from this exactly: it has other objects, another graph and another order, and delta chains
depend on these. How a real server stores objects (its own gc, its own limits) cannot be seen either: it was not
touched.

## Merge semantics

`synth semantics` ([`synth/semantics.go`](scripts/gitgrowth/synth/semantics.go)) models two machines, A and B. Each
has two clones: an SQLite repository with the real merge driver (the `memcue` binary built from this tree) and an
event log repository. Writes go through `internal/store`. memcue takes the author from the host name, and both
machines run on one host, so new rows are marked `machine-a` / `machine-b` directly in SQL. The two machines share a
clock.

Each round is checked in both sync orders. The second order runs on a copy of the same state, with the remotes
redirected to the copy. Checks:

- both orders give the same base;
- **no lost and no invented versions**: the reference does not depend on `Merge`: every version of either side is
  present as many times as on the side that has it most, and nothing beyond that;
- version numbers are contiguous;
- index: the number of index rows equals the number of live facts (`IndexStats`). Counters are compared, not the index
  content;
- a repeated `Merge` of the inputs into the already merged base changes nothing;
- the same inputs through `git merge-file` for one JSONL file: a normal line merge and `--union`.

| scenario | round | both orders equal | no losses | index (counters) | repeated Merge | fact outcome | line merge conflicts | `merge=union` |
|---|---|---|---|---|---|---|---:|---|
| independent-adds | adds | yes | yes | yes | yes | — | 1 | ok |
| concurrent-correct | correct-both | yes | yes | yes | **no** (+1 row) | active, v3 from B | 1 | duplicate `(id, version)` |
| retire-then-correct | A retire, B correct later | yes | yes | yes | **no** (+1) | **active**, v3 from B | 1 | duplicate |
| correct-then-retire | B correct, A retire later | yes | yes | yes | **no** (+1) | retired, v3 from A | 1 | duplicate |
| reopen-vs-retire | A restore, B retire later | yes | yes | yes | **no** (+1) | retired, v4 from B | 1 | duplicate |
| retire-vs-reopen | B retire, A restore later | yes | yes | yes | **no** (+1) | active, v4 from A | 1 | duplicate |
| relabel-vs-queries | both edit the same version | yes | yes | yes | **no** (+1) | active, v3 from B | 1 | duplicate |
| relabel-revert | A changes a label and reverts it | yes | yes | yes | **no** (+1) | active, v4 from B | 1 | duplicate |
| repeated | 1: correct on both | yes | yes | yes | **no** (+1) | active, v3 | 1 | duplicate |
| repeated | 2: A retire, B correct later | yes | yes | yes | **no** (+1) | **active**, v5 | 1 | duplicate |
| repeated | 3: A retire again, B add | yes | yes | yes | yes | retired, v6 | 0 | ok |
| repeated | 4: no writes | yes | yes | yes | yes | retired, v6 | 0 | ok |

In every round the event log gave the same base as the driver, in both orders and without losses.

The conclusions apply only to these scenarios: two machines, one host, a shared clock.

1. **The current driver converges and loses nothing** in all twelve rounds: both orders give one base, and every
   version is in place. This does not cover other scenarios.
2. **Retire is not stronger than a correction.** If A retired a fact and B later by the clock corrected the same fact,
   the fact is active again after the merge. Locally `Correct` refuses on a retired fact, while `Merge` simply takes
   the last version by `created`. This is how the documented rule "the later change is current" works, but the
   outcome is decided by the clocks of two machines. Whether this resurrection is intended is a product question. Any
   new representation must either repeat this rule or change it explicitly and test it.
3. **A repeated merge duplicates a version.** The prefix comparison already goes by content, but position by
   position: version `i` of one side is compared with version `i` of the other. After the first merge B's correction
   sits at position 3 on A, and at position 2 on B, which has not pulled the merge yet. On the next merge the prefix
   ends at position 2, the tails are joined, and the version present in both tails lands in the result twice. The
   repeated `Merge` in the table is a direct call to `store.Merge`. The same thing was reproduced separately through
   a real `git merge` with the driver (`stale-side-writes-again`):
   1. A and B correct the same fact, B later by the clock.
   2. B pushes.
   3. A merges and pushes; B's correction becomes version 3.
   4. Before pulling, B adds one more fact and commits.
   5. Pull on B is a real merge: the result has 18 rows where 17 are expected, and the fact gets a v4, an exact copy
      of v3.

   The fact's current status did not change, but the history grows, and every such merge adds a new duplicate.
   Whether the live base has such duplicates was not rechecked in this work. A one-off check of a copy of HEAD during
   the original run found 0 groups of identical rows, but its script is not in the publication.
4. **A line merge of one JSONL file does not work without its own driver.** Even independent adds conflict: ULIDs
   grow with time, and both sides append lines to the end of the file. `merge=union` removes the markers, but in any
   round with divergence it gives two lines with the same `(id, version)`, and strict parsing rejects them. The git
   documentation warns about the same: union "tends to leave the added lines in the resulting file in random order
   and the user should verify the result" ([gitattributes](https://git-scm.com/docs/gitattributes)).

### Event log prototype

`text-events` ([`synth/rows.go`](scripts/gitgrowth/synth/rows.go)) works like this:

- each fact version is an immutable file `events/<xx>/<id>/<hash>.json`, where hash is the first 32 hex characters
  (128 bits) of the SHA-256 of its bytes;
- the file holds the row with the version number zeroed (the `version` field is present and equals 0) and the hash of
  the event it was written on top of (`parent`);
- the two machines only add files with different names, so git merges the directory without conflicts and without a
  driver;
- the version number is derived when the base is built: events go in causal order (after their parent), and among the
  ready ones the earliest by `(created, author, content, hash)` is taken first.

On parallel tails this is the order `Merge` gives. In all 12 rounds the result matched the driver. In the scenario
with a stale side the log gave the expected 17 rows without a duplicate: the same version is the same file.

What the prototype is not: there is no proof of correctness, only the listed scenarios were checked. If a machine's
clock goes backwards within one branch, `Merge` will reorder the versions by time, while the log keeps the causal
order; this case was not tested. On equal keys the prototype breaks the tie by hash, `Merge` by the order of the sides
(a stable sort). This did not show on two machines because they have different authors.

## Round-trip, migration, races

Everything in this section checks prototypes on a synthetic base, not memcue code and not live data. The checks show
that the listed properties hold in the listed cases. They do not prove readiness for use in the product.

### Lossless round-trip

`synth roundtrip` takes the final synthetic base (18 997 rows) and adds edge cases: a fact with retire and restore, an
expiry date, a newline, a tab, quotes, a backslash, Cyrillic, HTML characters in evidence. Two more rows in pre-#514
states (`candidate` with `prompt_version=3` and `provisional` with an expiry) were inserted directly in SQL.

The check: export → JSONL → strict parsing → import into a new file → comparison. Result:

- all 16 columns of all rows matched, a repeated export is byte-for-byte equal to the first;
- `IndexStats` matched (3 751 live facts; counters are compared), 300 of 300 searches gave the same ids, versions and
  BM25, `CardFacts` for two scopes returned the same facts (the card's input is compared, not the rendered card);
- `memcue dump` of both bases is identical, that is, a base built from text is readable by the current binary;
- export 138 ms, import with index rebuild 1 444 ms.

IDs, versions, metadata, scope, expiry date and the retired/reopened state (168 restore versions) were preserved.

The strictness of the parsing is limited. It rejects an unterminated last line, an unknown field, a duplicate
`(id, version)` and invalid JSON. Two cases were checked: a file truncated mid-line (without the last 20 bytes) and a
file with a conflict marker in the first line. What the parsing does **not** catch can be seen from the code of
`decodeJSONL`:

- truncation exactly at a line boundary: the result is a valid file with fewer versions;
- a missing field: it silently becomes empty or zero;
- a gap in the version numbers, and an empty file.

A real format needs an integrity marker (for example, a row count or a hash in a separate record). The prototype does
not have one.

`memcue dump` itself does not survive a round-trip. Evidence is searched for in the output as a substring for rows
where it is at least 40 characters long: 0 of 1 078 found. Author is not printed, and in 18 996 of 18 997 rows
`created` loses the fractions of a second. The base cannot be restored from dump, and this has to be kept in mind if
it is dump that someone wants to make the text source of truth.

### Interrupted migration

`synth interrupt` kills the import 40 times with `SIGKILL` at a random moment. The import writes to a temporary file
`<db>.importing` and renames it to the target only when whole (write alongside, fsync the file, rename, fsync the
directory). Result:

- in all 40 cases the target base stayed as it was; it never turned out either corrupt or new;
- the temporary file was left behind every time; the next import deletes it;
- the final import after all the kills completed fully.

What this test does not show:

- All 40 kills landed before the rename, because the import spends almost all its time inserting rows. The window
  between the rename and the directory fsync was never hit.
- `SIGKILL` kills the process, not the kernel: everything the process managed to write stays in the page cache. The
  test says nothing about a power loss or a system crash; recovery after them was not checked.
- The prototype's procedure was checked, not memcue code.

### Concurrent write and commit

`synth race` writes to the base continuously for 30 seconds through `internal/store` (7 501 writes) and meanwhile
copies the file byte by byte, without locks, as `git add` or `cp` do:

- of 128 raw copies, **46 failed** `PRAGMA integrity_check`;
- the journal existed at the moment of 127 copies;
- all 128 exports through a single read transaction are intact.

The number of corrupt copies depends on thread scheduling and varies between runs; in the quick run of the checks it
is different. The load here is a stress load: writing is continuous, while in normal work a commit at the end of a
session rarely coincides with a write. But dream runs in the background. SQLite explicitly names copying the file in
the middle of a transaction, and a copy without its journal, as paths to corruption
([howtocorrupt](https://www.sqlite.org/howtocorrupt.html), sections 1.2 and 1.4). The current scheme depends on the
owner's sync script not committing the base during a write. I have not seen how that script works: it is not in this
repository. Whether `memory/facts.db-journal` is ignored in the live repository, and whether it ever got into the
history, was not rechecked in this work.

`integrity_check` catches only structural corruption. A copy that passed the check can still hold half a transaction,
for example a `facts` row without its index row. Such logical inconsistencies were not counted.

### Vectors and index

- There are no vectors in the base: nothing in the product code writes to `fact_vectors`, and `Open` deletes vectors
  written by an old binary (#260). If vectors come back, under any variant their place is a local cache next to the
  derived base, not git: #260 already removed them from sync when they took about 40 % of the file.
- The index (`fact_index`, `fact_fts`, `facts_created`, `fact_index_numbers`, the autoindex) now travels in every
  blob. How much it takes in the real base is not kept in the published results. In the text scheme it does not get
  into git at all: on synthetic data, an import with an index build from 19 thousand versions took a second and a
  half.

## Comparison of the variants

| | SQLite + gc | batching | one JSONL | a file per fact | event log |
|---|---|---|---|---|---|
| product changes | none | none (sync setting) | new format, own driver | new format, own driver | new format, base build |
| history storage (replica, after gc) | 63.7 MiB (aggressive 25.1) | 19.1–34.8 MiB | 6.8 MiB (1.8) | 5.2 MiB | not built on the replica; synthetic 13.2 against 29.0 for SQLite |
| thin pack of all syncs (model, replica) | 23.4 MiB | 20.1–20.5 MiB | 1.7 MiB | 6.8 MiB | synthetic 12.6 against 15.1 |
| git conflicts on independent adds | no (driver) | no (driver) | yes, without a driver | no, different files | no |
| concurrent edit of one fact | driver | driver | driver required | per-file driver required | no conflicts |
| duplicate on a repeated merge | yes | yes | depends on the driver | depends on the driver | not in the checked scenarios |
| readable diff | textconv, lossy | same | yes | yes | yes, but per event file |
| corrupt copy during a write | possible | possible | export in a transaction | same | same |
| gc memory | 2.2 GiB (aggressive 4.1) | less | 1.4 GiB | 16 MiB | 26 MiB (synthetic) |

Batching shrinks the loose storage but does not change the encoding, and the gain after gc is small. Besides, fewer
commits also means a wider window in which two machines diverge. One JSONL compresses best of all the variants
(1.8 MiB after `gc --aggressive`), but git sees it as one file: any parallel changes conflict, and it does not work
without its own merge driver. A file per fact and an event log spread the changes across files, and git merges
independent adds on its own.

## Recommendations

1. **Now, without a product change: pack the storage.** On the replica `git gc` gave 605 → 64 MiB in 30 seconds with
   a peak of 2.2 GiB. On the live repository it was not checked, and there is no checked procedure here. If the owner
   decides to do it:
   - for the duration of gc, stop sync and memcue writes on that machine (hooks, cron, dream) so that nothing writes
     to the repository;
   - back up the repository directory;
   - run `git gc` **without** `--prune=now`. By default unreachable loose objects younger than `gc.pruneExpire`
     (2 weeks) are not deleted. The git documentation says directly that `--prune=now` "increases the risk of
     corruption if another process is writing to the repository concurrently" ([git-gc](https://git-scm.com/docs/git-gc));
   - after gc, compare `git count-objects -vH` with the expectation.

   `gc --aggressive` gave 25 MiB on the replica, but cost 77 seconds and 4.1 GiB; better not to run it on a small VPS
   or NAS. `git maintenance` (the `loose-objects` and `incremental-repack` tasks) **was not measured**.
   `transfer.unpackLimit=1` was checked on synthetic data and does not help. The server is worth checking separately;
   its storage cannot be seen from here.
2. **Batching commits only for the sake of history is not worth it.** Once a day instead of every session gives 19
   against 64 MiB after gc on the replica, and almost the same model transfer. The price is more uncommitted writes
   and more frequent divergence.
3. **Decide how `Merge` should treat a version present in the tails of both sides, before any format change.** The
   prefix comparison already goes by content, so "compare by content" alone fixes nothing. Directions worth
   considering: collapse identical (by `same`) versions when joining the tails, or rely on the base `%O`, which the
   driver now ignores. Both raise semantic questions. For example, two independently written but byte-identical
   versions would become one when collapsed. No fix is implemented or checked here. The `stale-side-writes-again`
   scenario and the repeated `Merge` from the table are ready cases for regression tests. This is a separate task; I
   did not open an issue for it.
4. **Long term: text as the source of truth, SQLite as a derived base.** Of the measured variants I would take a file
   per fact: on the replica 12 times less history and 3.5 times less model transfer than SQLite, merging of
   independent adds without a driver, gc in megabytes of memory. For a concurrent edit of one fact it needs a per-file
   driver with the same logic as `Merge`. An event log removes that too, and the duplicate in the checked scenarios,
   but makes more files and more transfer (synthetic: 12.6 against 6.9 MiB) and needs a build rule that was checked
   only on the scenarios above. The choice between them is the owner's. The `memcue dump` format does not fit as a
   source: it loses fields.
5. **Decide the rule of retire against a later correction** explicitly and pin it with a test, whatever format the
   facts live in.

## What a transition could look like

This is a plan, not a checked procedure. Only two of its parts were checked on a synthetic base: import with atomic
replacement (with the caveats of the "Interrupted migration" section) and reading the built base with the current
binary.

1. **Format version and barrier.** A format marker sits next to the text. A memcue that does not know it must not
   commit `facts.db` on top of a text history. Today an old binary refuses a base with a newer schema
   (`user_version`), but it knows nothing about text files. So a coordinated transition is needed: update all
   machines, then switch on the new format. Mixed operation of old and new versions without such a barrier is not
   supported.
2. **Phase one: text as a derived form.** memcue commits both `facts.db` and the text. The source of truth stays the
   same; the text is checked against the base on every sync. Rollback is simply to stop writing the text.
3. **Phase two: switching the source.** `facts.db` leaves the git index (`git rm --cached`, the history is not
   rewritten), and a new machine builds the base from the text. The import writes alongside and renames when whole; an
   import interrupted before the rename leaves the previous base.
4. **Backup and rollback.** Before the transition, a copy of the base through `VACUUM INTO` (as `Store.Backup` does).
   Rollback after phase two: build the base from the text and commit `facts.db` again. The current binary reads a
   synthetic base built from text: `dump` matched byte for byte.
5. **The existing history is not rewritten.** The old blobs stay; only gc shrinks them.

## Privacy

- The git history keeps every version of every fact, including retired ones. A fact deleted from the base stays in
  every clone and on every remote until the history is rewritten. That was not done here and is not proposed.
- In the SQLite blobs the facts lie as they are, only in binary form. In a text format they become readable through
  `git log -p` and the server's web interface. The risk is the same, but more visible: access to the repository is
  access to all facts over the whole history.
- Local clones and the remote are different storage places. gc on a clone does not shrink the server; deletion on the
  server does not touch the clones.

## How to watch the growth

The commands only read the repository:

```sh
git -C <repo> count-objects -vH                        # loose and pack
git -C <repo> rev-list --all --objects -- memory/facts.db \
  | git -C <repo> cat-file --batch-check='%(objecttype) %(objectsize) %(objectsize:disk)' \
  | awk '$1=="blob"{n++; s+=$2; d+=$3} END{printf "blobs %d, logical %.1f MiB, disk %.1f MiB\n", n, s/2^20, d/2^20}'
```

Signals: the number of loose objects grows while the pack does not, which means gc has not run. A "disk / logical"
ratio around 0.3 means the blobs are stored whole, without deltas.

## What was not measured

- The source commit graph and past traffic: the measurements were made on a linear replica, the transfer is a thin
  pack model and a local fetch over `file://`. The size of the source repository after gc.
- `git gc` on the live repository, concurrently with sync or writes.
- Storage on real servers (their gc and limits), traffic over SSH with its overhead.
- `git maintenance`, `git repack` with other windows, `pack.windowMemory`, `core.bigFileThreshold`.
- Batching by local days, and a real batching scheme with edits from two machines between commits.
- An event log on real data: it cannot be built from snapshots; it needs writes at the moment of the change.
- An SQLite `facts` table with rowid instead of `WITHOUT ROWID` and its effect on page fill and deltas.
- Logical (not structural) inconsistencies in raw copies; repeatability of times between runs (each variant was run
  once).
- An import interrupted after the rename, a power loss, a text file truncated at a line boundary.
- The index content after a merge (only counters were compared).
- Mixed operation of old and new binaries in the text scheme, the transition as a whole.
- The owner's sync script: when it commits and whether it can hit a write.
- Machines with different clocks, and scenarios with three or more machines, except `stale-side-writes-again`.

## Reproduction

Only the synthetic part can be repeated: the script of the real replica is not published (see "Method"). It needs go
1.27, git, Python 3.11+ and `prlimit` (util-linux).

```sh
docs/research/scripts/gitgrowth/run.sh SCRATCH RESULTS
```

`SCRATCH` and `RESULTS` are new paths: the script rejects an existing path or a symlink, and the parent must exist.
Neither may lie inside the source tree or contain it, and they may not nest in each other. The paths are checked after
resolving symlinks in the parents and before anything is created. Both directories are created with mode 0700. The
script removes all `GIT_*` from the environment, git reads neither the system nor the global config, hooks and
fsmonitor are turned off on the git command line, `TMPDIR` points inside `SCRATCH`. `synth` and `synthetic.py` follow
the same rules when run on their own: each `-out` is a new directory, each result file is a new file. The script
deletes nothing.

`synthetic.py` does not trust the repositories in `SCRATCH` either: `git gc --prune=now` on a repository whose `.git`
is a symlink or a gitfile would go into someone else's repository. So before the first git command it checks every
element of `--root`, and `gitmeasure.py` repeats the check before a measurement, before a push and on each copy before
gc. A repository is accepted only if it lies entirely inside the scratch directory and consists of regular files and
directories of the current user: no symlinks and no hard links. `.git` must be a directory. The git directory may hold
only the entries that `git init`, commits, push, fetch and gc leave: no `commondir`, `worktrees`,
`objects/info/alternates`, hooks other than `*.sample`. The config may hold only the keys that `synth` and
`gitmeasure.py` set, so `core.worktree` and `include` are rejected. Finally, `git rev-parse` must see the same git
directory and the same object store. The script rejects everything else as a whole and fixes nothing. There is no
protection against another process of the same user swapping the repository between the check and the git command:
the scratch directory must belong to the run.
The synthetic repositories stay in `SCRATCH`, and whoever ran it decides what to do with them. If the run is killed
with `SIGKILL`, everything it managed to write stays inside `SCRATCH`. In the report run the synthetic part with the
checks took about 21 minutes. `GITGROWTH_QUICK=1` reduces the workload to a trial run of under a minute; its figures
have nothing to do with the report.

At the end `run.sh` runs [`check.py`](scripts/gitgrowth/check.py) and fails if any assertion does not hold. The
checker checks what the report relies on: the round-trip, the interrupted import, convergence and no losses in each
merge round, the gc exit codes. It also checks the deterministic findings: the duplicate in
`stale-side-writes-again`, the resurrection in `retire-then-correct`, the evidence missing from dump. If a finding
stops reproducing, the report is out of date, and the checker returns a non-zero code too. Numbers that change from
run to run (corrupt copies, times, sizes) it does not check.

[`report.py`](scripts/gitgrowth/report.py) prints raw tables from the JSON results. The tables of this report were
assembled from them by hand: some columns are omitted or merged, and the semantics table and the prose were written
from them.

The published results are in [`scripts/gitgrowth/results`](scripts/gitgrowth/results) (aggregates only). All of them
come from the report run of 2026-10-27, before the security fixes in the scripts. The measurement logic did not change
with these fixes, but the full run was not repeated after them: only the tests and the quick run were. In
`semantics.json` the ids of synthetic facts in error messages are replaced with `<id>`. This is the same regular
expression that `synth` now applies.

Tool tests:

```sh
python3 -I docs/research/scripts/gitgrowth/test_gitgrowth.py                    # seconds
GITGROWTH_E2E=1 python3 -I docs/research/scripts/gitgrowth/test_gitgrowth.py    # plus a quick run.sh run
```

The tests check several things:

- `check.py` passes on the published results and returns 1 on each of the deliberately broken copies;
- the JSON has no ULIDs, long hex hashes or absolute paths;
- the scripts reject existing paths, symlinks and nesting, including `RESULTS` inside the source tree;
- `run.sh` exits with an error if `report.py` failed;
- `synthetic.py` and `gitmeasure.py` reject a hostile repository in scratch: a `.git` symlink and a gitfile to a
  sentinel repository, alternates, `commondir`, `worktrees`, `core.worktree`, `include`, a symlink inside `.git`, a
  hook. A control test shows that `git gc` through a `.git` symlink really does change the sentinel repository.

For the security check the test builds a sentinel repository and a hostile environment: `GIT_DIR`, `GIT_WORK_TREE`,
`GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_INDEX_FILE`, `GIT_TEMPLATE_DIR`,
`GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`, `GIT_CONFIG_GLOBAL`, `HOME` and `XDG_CONFIG_HOME` with hooks and
fsmonitor that leave marker files. A control test shows that without clearing, this environment really reaches git.
Under it the tools must leave the sentinel repository byte-for-byte unchanged, trigger no marker and write nothing
outside their own directories. The exception is toolchain caches in the substituted `HOME`: version manager shims and
Go telemetry. The scripts do not protect against other environment variables, for example `GOFLAGS`.

Individual steps, if not all are needed (`SCRATCH` and `RESULTS` already created, all paths absolute, each `-out` and
result new):

```sh
"$SCRATCH"/bin/synth workload -out "$SCRATCH"/synth -result "$SCRATCH"/workload.json
python3 -I docs/research/scripts/gitgrowth/synthetic.py --root "$SCRATCH"/synth \
    --workload "$SCRATCH"/workload.json --out "$RESULTS"/synthetic.json
"$SCRATCH"/bin/synth semantics -out "$SCRATCH"/semantics -memcue "$SCRATCH"/bin/memcue -result "$RESULTS"/semantics.json
"$SCRATCH"/bin/synth roundtrip -db "$SCRATCH"/synth/sqlite-every/memory/facts.db -out "$SCRATCH"/roundtrip \
    -memcue "$SCRATCH"/bin/memcue -result "$RESULTS"/roundtrip.json
"$SCRATCH"/bin/synth interrupt -db "$SCRATCH"/synth/sqlite-every/memory/facts.db -out "$SCRATCH"/interrupt -n 40 \
    -result "$RESULTS"/interrupt.json
"$SCRATCH"/bin/synth race -db "$SCRATCH"/synth/sqlite-every/memory/facts.db -out "$SCRATCH"/race -for 30s \
    -result "$RESULTS"/race.json
python3 -I docs/research/scripts/gitgrowth/check.py "$RESULTS"
```

The binaries in `$SCRATCH/bin` are built by `run.sh`; for individual steps they can be built with the same `go build`
commands as in it.
