# Anchors in agent search queries, November 2026 (#746)

**Agents already anchor their searches. In a read of 120 of the 972 distinct default `memcue search` queries from
this machine's Claude Code transcripts, 92 name the system (77%), 45 carry an exact identifier (38%), and 104 do at
least one of the two (87%). Only 3 of the 101 queries with a user message to judge lacked an identifier the message
held (3%, 95% interval 1–8%).** An instruction to copy identifiers from the task would reach that 3%, so stage 2,
the end-to-end replay, did not run. The session note is unchanged.

This is stage 1 of the issue: counts from the transcripts, no model runs. It follows [#745](message-rule-745-2026-11.md)
and uses the same calls.

## Data

[extract.py](scripts/anchors746/extract.py) reads the same transcripts and parses calls the same way as #745: Bash
calls with a literal query, outside temporary directories, with the default floor. This time it keeps queries of any
length: 993 calls, **972 distinct** by text, flags and directory, median 5 words. For each call it also keeps:

- the task: the last message the user typed before the call (slash commands, hook and command output and tool
  results left out). For 174 calls there is none, mostly in subagents.
- what the search printed at the time: facts for 363 calls and "No stored facts match." for 5. The other 604 sat in
  a command that ran several searches, whose joint output cannot be split per query.

No query or task text is in the repository. [sample.json](anchors-746/sample.json) and
[hand-read.txt](anchors-746/hand-read.txt) hold call IDs and labels only.

## The read

`random.Random(746)` drew 120 of the 972 calls. The agent of this session (Claude Opus 5.5) read each query with
its task and marked three things, as the user's instruction "давай брать 746" delegated it. This is the agent's
read, not a person's, and it is one pass:

- **S**: the query names the system it is about: a host, service, repository, product or tool (`loffe`,
  `headscale`, `perigee`, `Google Play`, `gradle`, a domain).
- **I**: the query carries an exact identifier that cannot be paraphrased: a command or flag, an environment
  variable, a path, a file, test or function name, an error string, a ticket, an issue number, a version, a port, a
  config key or a model ID.
- **G**: the query has no I, but the user's message held an identifier that bears on this search. It is not judged
  when there is no message (19 of 120).

| | count | share | 95% interval |
|---|---:|---:|---:|
| names the system (S) | 92 / 120 | 77% | 68–83% |
| carries an identifier (I) | 45 / 120 | 38% | 29–46% |
| both | 33 / 120 | 28% | 20–36% |
| at least one | 104 / 120 | 87% | 79–92% |
| neither | 16 / 120 | 13% | 8–21% |
| no I although the message held one (G) | 3 / 101 | 3% | 1–8% |

Of the 101 queries with a message, 61 carry no identifier, and in 58 of those the message held none either: a short
go-ahead or a question in plain words. All three gaps are identifiers the message named outright:
two ticket keys and one release version. A fact naming the ticket existed at the time of the search in both ticket
cases. For the version, the facts naming it were written a day after the search.

The system goes unnamed in 28 queries. In 21 of them the message can be judged, and only one named a system the query
lacks. Inside a repository the default search already covers that repository, this host and global facts (#418), so
most queries do not need the repository's name.

## A rule over all 972 queries

[count.py](scripts/anchors746/count.py) applies a deterministic rule for I. It looks for a token that is a path, a
flag, an environment variable, camelCase or snake_case, a file with an extension, a ticket, an issue number, a number
of three or more digits, or a dotted version. On the 120 read queries it agrees with the read on 107. It has 0 false
positives and 13 misses: identifiers such as a subcommand name, a git config key or a plugin name that look like
plain words. Over all 972 queries it finds an identifier in 271 (28%, 25–31%). That is a lower bound: the read finds
38% on its sample.

## The searches that found nothing

Of the five searches that printed "No stored facts match.", the rule finds an identifier in two. Of the other three,
two name their system. The one long query of #745 with no useful fact also carries an identifier. Missing
anchors do not explain most of these misses. Whether the base held an answer at the time was not checked.

## Why stage 2 did not run

The issue makes stage 2 conditional on stage 1 finding a gap. The proposed instruction asks for the system's name and
for any exact identifier or error text from the task. In this read the message rarely holds an identifier that the
query left out (3 of 101), and nearly never a system name the query left out (1 of 21). A replay of the #636 prompts
under such an instruction would compare arms that differ on a few percent of searches, below what #647's design can
resolve.

## Limits

- One reader, the agent, one pass; S and I are judgement calls at the edges (a tool name against a system, a
  subcommand against a word).
- The task is the user's last message. What the agent read in the repository or in tool output before the search was
  not judged. That context may hold identifiers too, such as error text from a failed command, so the 3% is the gap
  against the user's words only.
- Claude Code sessions on one machine over about two weeks; other agents are not in the set.

## How to rerun

```bash
D=docs/research/scripts/anchors746
python3 -I $D/extract.py ~/.claude/projects calls.jsonl
python3 -I $D/count.py calls.jsonl docs/research/anchors-746/sample.json docs/research/anchors-746/hand-read.txt \
  docs/research/message-rule-745/results.json queries-745.jsonl counts.json
```

`queries-745.jsonl` is the query file of #745's [extract.py](scripts/messagerule745/extract.py). A rerun on another
day reads other transcripts, so the sample IDs no longer point at the same calls; [counts.json](anchors-746/counts.json)
holds this run's counts.
