# A bench that holds the binary to what the docs say, October 2026

Status: **built 2026-10-26 ([#451](https://github.com/juev/memcue/issues/451)); 26 cases and 3 generators, all
green on 0.16.0.** The unit tests of `cmd/memcue` call the commands inside the test process. A flag that main parses
differently, an environment variable that leaks into a child, or a default that only the binary applies never
reaches them. The bench drives the built binary the way an agent does and reads only what a host parses.

## What the bench is and is not

It is `internal/bench`, a test-only package:
- `bench_test.go` is the harness. It builds the binary once per run, or takes `MEMCUE_BIN`. It gives every case its
  own base, state directory, Claude config directory and home, and makes repositories with git whose origin is
  `git@example.com:team/<name>.git`.
- `cases_test.go` is the case table, one subtest per case.
- `generators_test.go` derives subtests from a fixed seed set of facts: case forms, letter case and identifier
  mutation, cut and padded queries, and the latency check.

Every fact goes in through `memcue add` (or `import`, for the latency base) and comes out through `search -json`.
The human line is never asserted on: the key it shows is the fact's origin, not its scope, and its wording is free to
change. The facts are invented, `acme-*` projects and `example.com` repositories.

It is not a measurement of usefulness. Nothing here is labelled U/R/N, and nothing here says whether the agent finds
the right fact for a real question; that is the job of the research in this directory and of `search.log`. The bench
says that the binary keeps the promises the docs make about search, and that the behaviour recorded as intended has
not changed by accident.

## Protocol

- **A finding becomes a case.** A bug, a question in an issue, or a sentence a review doubts is turned into a row of
  the table before or with its fix, so it is checked on every run after.
- **A rule case names its sentence.** Its `note` quotes or names the sentence of README or docs that it holds the
  binary to. It must be green on main. A red rule case is a defect: it is filed and fixed in its own change, not
  silenced by editing the case.
- **A characterization case records intended behaviour.** It asserts what the binary does today, and its `note` says
  so and why. A characterization case going red is not a defect by itself: it says that the behaviour changed, and
  the change either goes into the docs together with the case, or is reverted.
- **Every expectation is checked against the binary.** A case is written after the behaviour was seen, not from a
  reading of the code. A case that cannot fail is not coverage. The tie, the floor and the default place were checked
  by building mutated binaries outside the repository: each mutation turns its case red.

## Adding a case

1. Add a row to `cases` in `internal/bench/cases_test.go`:
   - an `id` in kebab-case;
   - the `stratum`, `rule` or `characterization`;
   - a `note` with the sentence or the reason;
   - a `setup` that names its facts with `w.add`;
   - an `action`, usually `one(query, opts)` or `inRepo(repo, query, opts)`;
   - an `expect`.
2. `expect` names facts, not ids: `found`, `notFound`, `order` (pairs, first before second), `most` (a cap), `none`
   (no fact at all), `shape` (the `-json` contract), and `also` for a check of its own.
3. Run it against the binary: `go test ./internal/bench -run 'TestCases/<id>' -v`.
4. When the same rule holds for many inputs, add the input to a generator instead: its subtest is named by the input.

`make bench` runs the package alone and lists every case. `make test` runs it too, under `go test -race ./...`.
`MEMCUE_BIN=/path/to/memcue make bench` judges another build, a release or another branch's binary, with the same
cases.

## What the first run showed

On 0.16.0 every case and every generated subtest is green: 26 cases (23 rule, 3 characterization) and 43 generated
subtests.
- **Stemming and letter case.** Every case form of `релиз` and `сборка` tried, the verb forms of `собирать` and
  `подписывать`, and `РЕЛИЗ` keep the fact.
- **Identifiers.** `hledger-vscode` in any letter case, and the cut `hledger-vscod`, keep the fact.
- **Versions.** `v2.15.0`, `v2.14.1`, `v2.13.0`, `v3.14.0`, `v2.14` and `2.14.0.1` are not served as the fact
  about `v2.14.0`, even with the floor off.
- **Truncation.** A query cut to two words, and one padded with twenty unrelated words, keep the fact in the top 5.
- **Latency.** On 1000 synthetic facts, the 95th percentile of 20 searches was 14 ms, process start included, with a
  median of 9 ms; the budget is 250 ms.

The characterization cases record:
- **A paraphrase is served next to its original.** Search merges nothing; duplicates are the dream's and the
  review's job.
- **An empty base answers quietly.** Exit 0 and nothing on stderr. With `-json` stdout is `[]`; without it, stdout
  is one line, `No stored facts match.`. The message is on stdout, not on stderr.
- **A query nothing fits returns no fact.** With `-json` the answer is `[]`. Without it the answer is a hint, which
  inside a repository names `-in all`.

Two points differ from what #451 assumed:
- `search -json` has no `text` and no `kind` field. Its fields are those of `searchFact` in `cmd/memcue/facts.go`:
  `id`, `content` and `created` always, `keywords`, `origin`, `scope` and `expires` when set. The shape case holds
  the binary to that.
- `-kind` therefore cannot be checked through the kind field; the case checks which facts come back.

One behaviour was seen and left out of the table: with `-json`, an empty answer carries no hint at all. The shelf hint
of #433 (`1 fact on the shelf matches: -in shelf:research`) is printed only on the human output, and the Hermes and
DSH tools call `search -json`. Whether that is intended is a question for an issue, not for a characterization case.

## Limits

- **Only the deterministic part.** Extraction, the review, the dream and anything else a model decides are out of
  scope: their answers change from run to run, and a bench that pins them would pin a sample.
- **Synthetic facts.** A few dozen invented facts per case, 1000 generated ones for the latency. A real base has
  thousands of facts with shared vocabulary, and BM25 on it may order the same facts differently.
- **The CLI cannot backdate a fact.** So `-since` is checked at the day boundary: today keeps a fact added today,
  tomorrow drops it.
- **Temporary directories name no project.** A global fact is made with `-scope global` and has an empty origin, so
  the tie case checks the project fact against that fact, not against an origin of the Claude config directory.
- **Latency counts process start.** That is what an agent waits for, but on a loaded machine it is mostly the start.

## Reproducing

```sh
make bench                                   # build from this tree, run every case
MEMCUE_BIN=/path/to/memcue make bench        # the same cases against another binary
go test ./internal/bench -run 'TestCases/project-before-global-on-tie' -v
go test -short ./internal/bench              # without the latency check
```
