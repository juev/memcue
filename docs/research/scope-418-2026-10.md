# The scope of a search: a suffix key and the repository default, October 2026

Status: **measured on a live base, 2026-10-26.** Two changes to [#418](https://github.com/juev/memcue/issues/418), one
measurement each. The base is a copy of the live one: **391 live facts** by id (`status='active'`,
`review IN ('','provisional')`), 176 characters on average, **255 of them carry the host scope** and 4 are candidates.
Names of private repositories, hosts and services are replaced by placeholders; the numbers are the ones the run gave.

## `-in repo:KEY`: the key may be the end of the stored one

The stored scope is the whole key — `repo:github.com/…/memcue` — and the base also carries a short key of the same
repository on old rows: `repo:memcue`. Before this change the short key returned nothing, because the filter compared
the two strings and the short one is not stored:

```sh
memcue search -json -n 3 -in repo:memcue -- "search stand"   # 0.14: [] — a wrong key and an empty base look alike
```

Now a key that matches nothing is an error naming the stored keys, and a key that is the end of exactly one stored key
is resolved to it:

| call | before | now |
|---|---|---|
| `-in repo:memcue` | no fact | 1 fact (the stored key ends with `/memcue`; the short key is not stored) |
| `-in repo:nothing` | no fact, exit 0 | exit 1, `no stored repository key ends with "nothing"; known keys: …` |
| `-in repo:<two keys end the same way>` | no fact | exit 1, the two keys named |

The message lists at most twelve stored keys and counts the rest. The stored keys of this base, live facts only, are
four: the memory repository under the full key, the research one, the configuration one and the note-taking one.

## The default inside a repository: the project, the host and the global facts

The binary's default in a repository was the project's facts alone. On this base that is 1 of 391 facts, while the host
scope alone holds 255, so a repository session saw a question about the host answered by a fact about the repository, or
not answered at all. Measured through the binary from a checkout of the memory repository, one question about the
installed binary and its wrapper, top five:

| | 0.14 (before) | this change |
|---|---|---|
| default | 1 fact, about the repository | **5 facts, the same set `-in all` returns** |
| `-in all` | 5 | 5 |

The host scope is only found when the harness names the host: the facts of this installation are `host:<name>`, the
container's own host name is a container id, and `MEMCUE_HOST` is what bridges the two. With `MEMCUE_HOST` unset the
default still answers one fact — the project's — because the host facts are not this machine's by name. Hermes passes
the name from its config (`memory.memcue.host`); a harness that does not pass it keeps the old behaviour, and that is a
deployment fact, not a search one.

The new default is stated in the session note, in the tool description of every harness that hands the search to a
model, and in the empty answer, which now reads `No facts of this repository, this host or global match; -in all
searches every repository.`

## Tests

`go vet ./...` clean, `go test ./...` all packages ok: `ResolveRepos` (exact key, suffix, no match, two matches, a
non-repository place, an empty key list), `RepoScopes` (sorted, no duplicates, retired and candidate facts excluded, a
host scope not returned), the new default (a global, a host and a project fact found from a repository session; the
whole base outside one) and the empty-answer message.

## What is not measured

A second base, a second labeller, and the harnesses other than the binary and Hermes: the eight agent queries and the
twenty user prompts in [pull-hermes-014](pull-hermes-014-2026-10.md) run with `-in all` on both arms, so the scope
change does not move them.
