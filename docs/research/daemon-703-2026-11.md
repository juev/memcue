# A long-lived memcue daemon, November 2026 (#703)

**A local replica removes almost all the cost of the PostgreSQL backend. Over the tailnet a search falls from 767 ms
to 28–41 ms, session-start from 862 ms to 16–31 ms, pre-command from 1184 ms to 30–54 ms. Serving the calls through
the daemon's socket gains only 10–25 ms over an ordinary CLI process that opens the replica file, because about 9 ms
of every call is starting the memcue process itself. LISTEN/NOTIFY keeps the replica within 0.23 s of a write made
on another machine (p95 0.25 s); polling every 2 s gives 1.3 s (p95 2.2 s). Recommendation: a sync process that keeps
a SQLite replica current (variant 2's snapshot and delta, variant 3's direct reads), with NOTIFY and a safety poll,
hosted in the existing tailnet helper for embedded mode. The text backend needs no daemon; its session-start is slow
for a reason a daemon would only hide.**

This is the research of [#703](https://github.com/juev/memcue/issues/703). It follows the server-side search of
[#700](https://github.com/juev/memcue/issues/700). The owner's decisions of 2026-11-10: prototype all four variants;
measure PostgreSQL on a separate research base and remove it afterwards. Production, defaults and the PostgreSQL
schema are unchanged. Implementation is a separate decision.

## Stand

- Mac (Apple silicon, macOS 27), memcue built from `main` at 7216375 with the prototype below.
- 10,000 synthetic facts from [gen_facts.py](scripts/daemon703/gen_facts.py), shaped after aggregate statistics of
  one real text base (3,737 active facts): content length p10/p50/p90/p99 = 112/286/609/950 bytes, the real
  proportions of kinds and of repo/host/global/shelf/service scopes, 45 repositories, 5 hosts. No real content.
  Current payload in PostgreSQL: 7.3 MB.
- Text base: the same facts loaded by `add -batch` into a text history (39 MB, cache 12 MB).
- PostgreSQL 18.6 on loffe, cluster `memcue-research-postgres`, a separate schema `memcue` in database
  `memcue_research`, filled by `migrate -postgres`. The production database was only searched read-only for a network
  check and never written. The schema and its NOTIFY trigger were dropped after the measurements.
- The Mac reaches it through the embedded tailnet helper. Round trip (`SELECT 1`) 85 ms; a new connection
  (helper dial, startup, SCRAM) 415–440 ms, about five round trips. Probed by [netcost](scripts/daemon703/netcost/main.go).
- Writes from another machine: loffe runs a linux build of the same tree and adds facts directly over its host
  network, one every 1.3 s.

Each figure below is the median and p95 of 30 calls (10 queries × 3) from [bench_cli.py](scripts/daemon703/bench_cli.py),
which starts a new process per call, as a hook does. The harness itself (`/usr/bin/time` and a bash wrapper) adds
about 5.5 ms; a bare `memcue version` takes 9 ms.

## The prototype

Built only with `-tags research`; the default build is unchanged.

- [daemon703_research.go](../../cmd/memcue/daemon703_research.go): `memcue daemon703 serve` keeps a local SQLite base
  as a replica of the source and answers `search`, the store read of `session-start` (the repository's pitfalls), the
  store read of `pre-command`, `add` and `stats` over an owner-only Unix socket. `memcue daemon703 call` is the client a
  hook would run.
- [research703.go](../../internal/store/research703.go) writes facts into the replica under their own ids and
  versions and refreshes the index; [tailnet research703.go](../../internal/tailnet/research703.go) runs the tailnet
  node inside the daemon for variant 4.
- Change detection: a poll of `count(*), sum(version)` (one round trip), then a delta that compares every
  `(id, version)` with the replica and fetches the differing payloads. Schema 2 has no change sequence, so this scan
  is the cheapest exact catch-up it allows. Or LISTEN on a trigger that sends `id:version` on insert and update.

The daemon's search answer equals the CLI's: the same ids in the same order for 10 of 10 queries before any write
was made. Its pre-command answer is the whole hit list; the CLI's packet is an ordered subsequence of it in 10 of 10,
cut by the response budget. The daemon does not implement the budget or the receipt file. Later runs differ from the
first only by two neighbours swapping places after 66 probe facts joined the base and moved the BM25 statistics.

## Latency of the hot calls

| | search | session-start | pre-command |
|---|---|---|---|
| Text base, CLI today | 37 / 43 ms | **289 / 302 ms** | 51 / 57 ms |
| PostgreSQL over the tailnet, CLI today | 767 / 819 ms | 862 / 885 ms | 1184 / 1216 ms |
| V1: memory replica, through the socket | 29 / 34 ms | 17 / 18 ms | 31 / 37 ms |
| V2: file replica, through the socket | 34 / 42 ms | 19 / 28 ms | 38 / 44 ms |
| V3: file replica, ordinary CLI reads it | 41 / 47 ms | 31 / 34 ms | 54 / 62 ms |
| V4: memory replica, node inside the daemon | 28 / 32 ms | 16 / 18 ms | 30 / 34 ms |

The text base's session-start reads every version of the history and parses every fact file on each call
(`repositoryVersions` in `cmd/memcue/session.go`, #686), so its cost grows with the base: 289 ms at 10,000 facts. The
same path serves `session-card -pitfalls-only`, which the Codex plugin runs before every shell command. The cause is
deliberate: another adapter may write through a different cache, and an appended correction does not change the
directory time that the ordinary open checks. A daemon hides the cost; a cheaper freshness check would remove it.

The 767 ms of a PostgreSQL search splits into a new connection (≈430 ms), two statements (≈170 ms) and the process,
helper status check and decoding. A measurement on the production base on 2026-11-09 gave 260 ms for the same command;
on 2026-11-10 the production base gave 650–680 ms, like the research base. The difference between the two days is not
explained.

## Start, restart and memory

| | start until the socket answers | peak RSS | after start |
|---|---|---|---|
| V1, PostgreSQL, cold | 3.4–3.5 s: connection 0.43–0.52, load 1.96 (fetch 0.33–0.43, index ≈1.5), writer connection 0.51 | 81–86 MB | 20 MB (`ps`), Go heap 6 MB |
| V2, PostgreSQL, cold into a file | 3.9 s | 58 MB | |
| V2, PostgreSQL, warm restart | 2.0 s: open 7–66 ms, connection 0.43–0.51, delta 0.49 (no changes), writer 0.51–0.56 | 34–35 MB | |
| V4, PostgreSQL, cold | 5.4 s: node up 2.1, first connection 0.74, load 2.0 | 96 MB | 100 MB |
| Text history into memory, cache present | 1.08 s | 77 MB | |
| Text history into memory, no cache | 5.0 s (cache build 3.9 s) | 88 MB | |

- The index build, not the network, dominates a cold start: 10,000 facts arrive in 0.33–0.43 s.
- The first warm restart after a killed daemon opened its replica in 1.58 s and caught up in 1.36 s; three later
  restarts took 7–66 ms and 0.49 s. Hypothesis, not checked: recovery of the journal the killed process left.
- A warm restart catches up writes made while the daemon was down: 5 of 5.
- With a change sequence column the catch-up would be one statement over the changed rows instead of a scan of
  10,000 `(id, version)` pairs (0.25 s while running, 0.49 s on a fresh connection). Writing through the sync
  connection instead of a second one would save the 0.5 s writer connection.
- For the text backend a memory copy is unnecessary: the existing SQLite cache opens in 4 ms.

## Staleness after a write on another machine

| | median | p95 | max | n |
|---|---|---|---|---|
| poll every 2 s, then delta | 1274 ms | 2183 ms | 2252 ms | 20 |
| LISTEN/NOTIFY, then fetch of that fact | 234 ms | 252 ms | 295 ms | 20 |
| LISTEN/NOTIFY, node inside the daemon (V4) | 227 ms | 253 ms | 286 ms | 20 |

Staleness is the time from the writer's `Created` (taken before its transaction) to the replica commit on the Mac,
corrected by the measured offset between the Mac and the server clocks (6–7 ms, NTP on both). A poll costs one round
trip (92 ms) whether or not anything changed; the delta that follows a change took 246 ms. NOTIFY needs a trigger,
which is a schema change; it reaches only clients connected at the time, so a restart or a lost connection still
needs the catch-up above.

## Writes and fallback

- `add` through the daemon: 557 ms, against 1013 ms for the CLI over PostgreSQL, because the connection is already
  open. The daemon applies its own write to the replica before it answers, so a search right after it finds the fact
  (5 of 5). The expected-version checks and ambiguous-commit errors stay those of the store's remote write path.
- A client whose daemon is not running learns it from `connect: no such file` and exits within the process start
  (8 ms), so the direct path can follow at once and the four-second budget is untouched.

## The variants

**1. Memory only, full load on start.** With V4, the fastest reads of the latency table, and the simplest model. Every start pays the full
load and index build, 3.5 s over the tailnet; peak RSS 81–86 MB. Nothing survives a restart.

**2. Memory plus a disk snapshot.** The replica is a SQLite file; a restart opens it and fetches the changes, 2.0 s
here and about 1 s with a change sequence and one connection. Reads through the socket are 6 ms slower than V1's.
Smaller RSS (35 MB warm), because SQLite pages live in the file cache.

**3. Daemon as a replicator.** Clients open the replica file with the existing local code: no IPC, no new protocol,
no second implementation of the commands. Reads are 7–24 ms slower than through the socket, still 20–40 times faster
than today's remote calls. The open question of the issue is real: a client cannot tell a stale replica from a fresh
one unless the daemon leaves a mark. A heartbeat stamp in the replica (the time of the last successful sync) lets a
client use the replica only when it is fresh and take the direct path otherwise. A client's own write would go to
PostgreSQL as today and then into the replica, or through the daemon.

**4. Daemon inside the tailnet helper.** Measured as the tailnet node running in the daemon's process. Reads and
staleness are those of V1 within noise; the node adds 2.1 s to a cold start and about 15 MB of RSS. What it gains is
one long-lived process instead of two and the helper's existing lifecycle: `connect up`/`off`, the ownership lock and
the owner-only socket. It applies only to embedded mode; a DSN reached without the tailnet needs its own process.

## Recommendation

For the PostgreSQL backend, a sync process that keeps a SQLite replica under the base's state directory:

1. Variant 2's persistence: the replica survives restarts and catches up by delta.
2. Variant 3's reads: hooks and the CLI read the replica directly when its heartbeat is fresh, and go to PostgreSQL
   otherwise. No command is reimplemented in the daemon, and the plugins do not change. Serving reads through the
   socket would add a protocol for 10–25 ms.
3. Writes: through PostgreSQL as today, applied to the replica at once so a client reads its own writes.
4. Change detection: a NOTIFY trigger plus a slow poll (for example every 30–60 s) as a safety net after reconnects,
   and a change sequence column so a restart catches up over the changed rows only. Both are a schema change (schema
   3) and need their own decision.
5. Hosting: inside the tailnet helper for embedded mode, reusing `connect up`/`off`, the lock and the socket; a
   standalone `memcue` process for a directly reachable DSN. Lifecycle by explicit command or service manager rather
   than on demand, as the helper does today.

For the text backend, no daemon. A search is 37 ms, most of it process start. session-start's 289 ms at 10,000 facts
comes from rereading the whole history and is worth a separate issue: a cheaper check that the cache covers every
file (sizes and times of fact files, or a stamp that every adapter updates) would make it a query like PostgreSQL's.

Version skew: the replica carries the SQLite cache schema; a client that finds another schema version takes the direct
path, and the daemon rebuilds the replica after an upgrade (a cold start, 3.5 s). Several bases: one replica and one
sync process per DSN profile, as the state directory is already keyed. Security: the replica is an owner-only file
holding what the database role may read, as a text base holds it today; the daemon applies no access rule a direct
open would not.

## Not verified

- Only the Mac as a client and only synthetic content; loffe and Hermes as clients, and a real base's vocabulary, were
  not measured.
- One client at a time: concurrent hooks reading the replica while the daemon writes were not stressed.
- NOTIFY over a lost and restored connection; long-running memory growth; macOS sleep.
- The pre-command packet budget and receipt state inside the daemon (the daemon timed only the store read).
- Variant 4 owned the identity of a stopped helper; the helper's own code was not extended.

## Reproduce

```bash
python3 -I docs/research/scripts/daemon703/gen_facts.py 10000 facts.json
go build -tags research -o memcue-r ./cmd/memcue
# a text base: MEMCUE_FACTS=<dir> memcue-r add -batch facts.json
# a PostgreSQL base: MEMCUE_FACTS=<dir> MEMCUE_POSTGRES_DSN=<research DSN> memcue-r migrate -postgres -apply
memcue-r daemon703 serve -sock d.sock -replica :memory: -source pg -notify      # V1; a file path for V2/V3
python3 -I docs/research/scripts/daemon703/bench_cli.py LABEL <wrapper> <repo dir> 3
go run -tags research ./docs/research/scripts/daemon703/netcost
```

The NOTIFY trigger used in the research schema:

```sql
CREATE FUNCTION memcue.notify_change() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN PERFORM pg_notify('memcue_facts', NEW.id || ':' || NEW.version); RETURN NULL; END $$;
CREATE TRIGGER facts_notify AFTER INSERT OR UPDATE ON memcue.facts FOR EACH ROW EXECUTE FUNCTION memcue.notify_change();
```
