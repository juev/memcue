# Цена открытия текстовой истории, октябрь 2026

Статус: **замеры для [#557](https://github.com/juev/memcue/issues/557), 2026-10-28; исправление в том же PR.**

Коротко:

- После перехода на текстовую историю ([#530](https://github.com/juev/memcue/issues/530)) поиск стал медленнее на
  2–4 мс ([release-0-22-0-555](release-0-22-0-555-2026-10.md)). Почти вся прибавка — две записи stamps в
  `syncText` при каждом открытии, даже когда ничего не изменилось. Каждая запись — отдельный commit с fsync.
- На диске loffe (ext4 на md RAID) `syncText` стоил 2.0 мс, из них 1.45 мс — две записи. Flock, чтение каталогов,
  чтение stamps, `count(*)` и пустая транзакция вместе — около 0.2 мс.
- Теперь stamp пишется, только когда его значение меняется. Поиск на копиях баз на диске loffe: 20.2 → 16.7 мс
  (файловая база — 15.9 мс) и 13.0 → 10.4 мс (9.8 мс). `syncText` — 0.23 мс.
- Остаток к файловой базе — 0.4–0.8 мс: это flock, чтение каталогов и `count(*)`, то есть цена проверки того, что
  принёс git.
- Отдельное наблюдение, не исправлялось: на Mac поиск по кешу, собранному из текста, медленнее поиска по кешу,
  скопированному с файла, на 0.3–0.7 мс. `optimize` FTS5 и `VACUUM` разрыв уверенно не закрывают.

## Метод

Копии баз, живые базы не пишутся:

- Mac: текст `~/.claude/memory/facts` (4712 файлов) и кеш, снятый `sqlite3 .backup`;
- loffe: те же данные из `~/.claude` на loffe;
- Hermes: текст базы Hermes (983 файла).

Для каждой базы есть файловый вариант (`file.db`, копия кеша) и текстовый (каталог `facts` и кеш в своём
`MEMCUE_STATE_DIR`). Команды, чтобы разделить затраты:

1. Временный тест в `internal/store` (не в репозитории): `Open(cache)` против `OpenText`, затем по отдельности flock,
   `textDirs`, чтение stamps, `begin + count + commit`, `saveStamp`, `saveTextRows` и `syncText`. По 30 повторов,
   медиана и p90.
2. Временные таймеры в `withStore` CLI (не в репозитории): открытие, поиск и закрытие внутри одного `memcue search`.
   По 100 запусков, файл и текст поочерёдно.
3. Весь процесс `memcue search -n 5 "hermes loffe docker"`. Сравниваются 0.22.0 и исправление, на файле и на тексте,
   по 100–120 запусков поочерёдно; медиана.

Первый прогон на loffe шёл в `/tmp` (tmpfs, fsync бесплатен) и показал разницу 0.6–1.0 мс. Повтор в `$HOME`
(ext4) показал 2.8–4.0 мс, как в проде: цена fsync видна только на настоящем диске.

## Разбор до исправления

Фазы одного `memcue search` на диске loffe, медиана, мс:

| база | открытие файла | открытие текста | поиск по файлу | поиск по тексту |
|---|---|---|---|---|
| loffe (4712 фактов) | 4.62 | 8.62 | 7.49 | 7.70 |
| Hermes (983 факта) | 1.54 | 4.37 | 4.21 | 4.40 |

Сам поиск стоит одинаково; разница целиком в открытии. Шаги `syncText` на том же диске, медиана, мс:

| шаг | loffe | Hermes |
|---|---|---|
| flock | 0.007 | 0.007 |
| `textDirs` (32 каталога) | 0.062 | 0.074 |
| чтение двух stamps | 0.040 | 0.051 |
| `begin + count(*) + commit` без записи | 0.097 | 0.039 |
| `saveStamp(text-dirs)` | 0.720 | 0.717 |
| `saveTextRows` | 0.748 | 0.718 |
| `syncText` целиком | 1.982 | 1.675 |

## После исправления

`syncText` на диске loffe: 1.98 → 0.23 мс (loffe), 1.68 → 0.30 мс (Hermes).

Весь процесс `memcue search`, медиана, мс:

| где | база | 0.22.0, файл | 0.22.0, текст | исправление, текст | исправление, файл |
|---|---|---|---|---|---|
| loffe, диск | loffe | 15.94 | 20.20 | 16.74 | 15.93 |
| loffe, диск | Hermes | 9.81 | 13.00 | 10.38 | 9.78 |
| Mac | Mac | 12.63 | 14.51 | 14.09 | 12.71 |
| Mac | Hermes | 9.89 | 10.64 | 10.26 | 9.94 |

На Mac fsync дешёвый, и записи stamps стоили там около 0.45 мс. Поэтому исправление дало на Mac меньше, чем на
loffe.

## Кеш, собранный из текста

На Mac у текстового варианта кеш собрал первый запуск из текста, а не скопировал с файла, как на loffe. Он на 3 МБ
больше (34.7 против 31.6 МБ). Поиск исправленной сборкой, медиана, мс:

| кеш | поиск |
|---|---|
| файловая база | 12.82–13.23 |
| текст, кеш скопирован с файла | 13.22–13.65 |
| текст, кеш собран из текста | 13.87–14.36 |
| то же после `INSERT INTO fact_fts(fact_fts) VALUES('optimize')` | 14.10 |
| то же после `VACUUM` | 14.01 |

Два прогона дали разницу 0.3–0.7 мс между собранным и скопированным кешем; `optimize` и `VACUUM` укладываются в
тот же шум. Причина не установлена. Гипотеза, не проверено: другой порядок строк и страниц после сборки одной
транзакцией. Эффект меньше погрешности этих замеров на Mac: в соседней сессии работал эмулятор Android.

- Mac был нагружен соседней работой, разброс там больше, чем на loffe.
- Живые базы после исправления не замерялись: исправление войдёт в следующий релиз.
