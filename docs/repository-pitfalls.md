# Automatic repository pitfalls

This is a narrow data channel: all latest active, UTC-nonexpired `kind=pitfall` facts explicitly scoped to the current
repository are delivered whole. Origin alone never grants applicability. Current remote aliases intentionally share
explicit scope; linked worktrees use the same repository identity. Non-git contexts load no repository facts. Rules,
decisions, host/global/service data and research shelves remain on their existing paths. No storage/schema migration,
model inference, ranked query or top-k selection is added.

`session-card -pitfalls-json` returns one complete native whole-fact snapshot. A read failure exits nonzero without
partial output. Content and framing are separate fields. Historical versions in text and pending cache writes are
read together because append-only corrections can otherwise leave another adapter's cache stale. Snapshots name
repository applicability and supersede earlier snapshots; they remain data whose conditions must be checked.

## Claude Code

The selected and natively validated release is **2.1.301**. Public Mods support is documented from CLI 2.1.287
(Desktop 2.1.286), but older clients are not claimed as verified integration versions. The ordinary instruction
command hook remains separate. `hooks/register.js` registers `classic.SessionStart` and `classic.UserPromptSubmit`, plus `classic.PostToolUse` after actual cwd changes:
one function call reads one snapshot and appends a dynamically sized `additionalContext` array, preserving all
`await next(e)` result fields. There is no fixed number of chunks, no fact truncation and no cross-hook repacking.
A prompt or a cwd change re-sends the snapshot only when its content differs from the one already delivered in
that session; session start, `/clear` and compaction always deliver it, and a failed read forgets the delivered
one, so the next boundary delivers again (#712).

Facts longer than the classic string ceiling travel whole through `prompt.context` blocks on initial/rebuilt context,
or additive `prompt.submit` / `tool.call` context for subsequent tasks and actual cwd changes. First-message blocks
are not invalidated during ordinary inference. Cwd is read from the host's `session.cwd` API after a tool returns;
this does not predict a future tool target. The original tool result is retained. Classic hook activation is required
before the tool-context path runs, so it is not a fallback around filtered lifecycle hooks.

Real API boundaries are explicit:

- `process.run` has 4 MiB stdout/stderr ceilings and truncation flags. Any truncation, failed child or malformed
  snapshot returns an unavailable diagnostic, without treating a subset as delivered. `MEMCUE_BIN` may name the
  configured executable; otherwise `memcue` must be on the host's PATH. The CLI must be built with this integration.
- Classic strings above 10,000 characters use the whole-block path, conservatively counting JavaScript UTF-16 units.
  Only the larger fields of the same snapshot use additive prompt/tool context with the public
  100,000-per-string / 200,000-total ceiling; small facts remain in the dynamic classic array. Unsupported whole snapshots
  are reported with no subset. Large initial context blocks avoid the command-string preview path.
- With managed settings or Team/Enterprise credentials, `sec-default` filters user-installed classic and context
  hooks. Organization deployment must explicitly manage/allow this mod through supported policy. The integration
  does not change that policy, trust, safe mode, or `disableAllHooks`. Native validation reports this guard.

Official contracts: [mods reference](https://code.claude.com/docs/en/plugins/mods/reference),
[overview](https://code.claude.com/docs/en/plugins/mods/overview),
[administration](https://code.claude.com/docs/en/plugins/mods/admin).
The public main declarations were generated by 2.1.277 and are not used as proof of the selected release: native
`plugin validate` and `plugin test` exercise the actual 2.1.301 engine and registered events. External CLI responses
are deterministic engine fixtures; persisted selection is separately verified against the real Go implementation.
No paid model call or live plugin installation is part of these checks.

## Hermes

**0.17.0** is the first inspected published release exposing normal-plugin `register_middleware('llm_request', ...)`;
0.16.0 lacks it. A separate ordinary plugin, `memcue-context`, registers through that supported normal loader. This
avoids requiring the older memory-provider collector to forward middleware registration. Install both directories:

```sh
cp -r plugins/hermes/memcue plugins/hermes/memcue-context "$HERMES_HOME/plugins/"
hermes plugins enable memcue-context
```

Set `memory.provider: memcue` as in the existing provider setup. These are normal required installation/activation
steps, not an optional automatic-recall toggle. Tests use isolated configuration rather than changing a live profile.
The normal plugin only uses an initialized primary provider instance bound to the exact active home/session. Ownership
is weakly held, rekeyed on session switch, and released on shutdown. The active provider configuration is checked on
every request. Subagents, other providers, unowned sessions and other profiles receive no facts from that owner.
Native state is bound to the owner's profile and base, preventing an inherited state directory from merging caches.

Each provider request reads the actual `agent.runtime_cwd.resolve_agent_cwd()` value. A copied request/list gets a
transient developer item appended after complete existing messages or Responses function-call/output items. Existing
system/history/tool output is unchanged; no extra user turn, forced retry or inference is introduced. An identical
last transient item is not duplicated; failed reads emit an unavailable item and subsequent requests read afresh.
Compaction and trivial prompts do not depend on turn-entry prefetch. In this mode the provider emits maintenance
hints and standing memcue instructions, with no duplicate automatic facts in its cached system/prefetch paths.

Legacy 0.15.2 search/tools remain supported, but startup explicitly reports that full automatic delivery requires
>=0.17.0 plus the companion. Legacy turn-entry retrieval does not claim the full mid-turn contract.
Real released 0.17.0 loader/dispatcher fixtures cover messages, Responses, same-turn cwd changes, protocol ordering,
trivial prompts, compaction, retry, failures, session rotation/shutdown, provider/plugin disablement, subagents and
same-session/repository identities in two distinct profiles. No core monkeypatch or host edit is used.
[Official middleware contract](https://hermes-agent.nousresearch.com/docs/developer-guide/middleware).

## Other integrations and verification limits

Codex retains supported start/task/Bash hook payloads and `additionalContextLimit: 0`. Relative target fields are an
accepted adapter extension, not the pinned native unified-exec payload; Python consumes them after one normalization
so Go does not resolve them again. Its inherited 4 MiB launcher ceiling is not a Codex host-limit claim.
DSH uses released peers 0.2.0-rc.2 and refreshes native context on task/cwd changes and compaction.
Full canonical tests and actual native model-free client/normal-loader fixtures are required before staging.
Live model transports, context-window capacity, and organization policy deployment are unverified without rollout.
